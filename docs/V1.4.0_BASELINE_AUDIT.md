## 9. Architecture decision record (v1.4.0 storage)

**Decision:** Replace the sql.js whole-state store with a relational schema (v5) on Node's
built-in `node:sqlite` (`DatabaseSync`) in the Electron main process; expose typed async IPC
operations; renderer becomes a paginated client; shared pure domain rules (`src/core.js`,
`src/domain.js`) imported directly by the ESM main process (single source of truth).

**Why objectively necessary (§7 allowance):** per-save full-DB rewrite + sync IPC + 200 MB cap
+ full renderer residency make 25k–100k-patient operation impossible (each save would rewrite
hundreds of MB and block the UI for seconds). No incremental fix exists within sql.js's
export-whole-database model.

**Why `node:sqlite` over better-sqlite3:** identical capability for this workload; zero native
packaging/ABI risk on Windows CI; sandbox-friendly (prebuilt downloads blocked here); present
in Node ≥22.13 and Electron 44's main process; keeps the app dependency-free at runtime.

**Migration & safety:** v4 `dentiva-pro.sqlite` (and `.bak`, and legacy JSON) are read with
`node:sqlite` (the sql.js export is a standard SQLite file), validated, converted inside a
transaction to v5 relational tables; the pre-migration file is preserved
(`dentiva-pro.sqlite.v4.bak`); on any conversion error the original file remains untouched and
the app falls back to read-only preserved mode. Orphaned records are quarantined, never
deleted. Rollback = restore the preserved v4 file (documented in MIGRATION guide).

**Caps policy:** remove `MAX_STORE_BYTES`; attachment max size becomes a setting
(default 256 MB) validated against free disk space (system-resource-aware, per §40);
diagnostics report DB size, free space, WAL size, integrity_check, orphan counts.
